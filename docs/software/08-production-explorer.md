## Persistence and compatibility

### Approved upload storage contract (UI-09, verified in installed 0.4.1)

Store newly uploaded originals in the authenticated user's Nextcloud home under `Media Storage/YYYY-MM-DD/`. Daily directories form a storage timeline and must not mirror virtual buckets/folders or subdivide by hour. Create missing directories on demand and reject inaccessible destinations; never overwrite an existing original. Validate upload permissions, MIME, size and quota on the server. The server captures the account core/timezone calendar day once, using UTC for missing/invalid settings. Multiple users have independent directories and virtual references even when their directory names match.

Upload adds an original and a virtual reference. Existing reference Move, Rename, Remove links, Clear contents and Delete bucket remain metadata-only. Users may later manage original files through Nextcloud; binding resolution must continue to use the file ID and validated storage context rather than depending on the dated path. A missing or inaccessible original must produce explicit unavailable/rebind feedback. This contract is implemented in prepared source 0.4.0; installed verification remains pending.

Keep the existing deterministic owner root as the default Library bucket. Existing IDs, parent relationships, bindings, virtual paths and token boundaries remain unchanged on populated 0.2 upgrades. Add ms_buckets (id/root_id, owner_id, name, name_key, created_at) for additional namespaces only. Additional roots are ms_nodes of type bucket with empty parent; name keys include owner identity to preserve the existing global sibling index. Names use NodeRules and exact UTF-8 equality. Bucket IDs equal their stable root node IDs. Lazy default Library is listed first without requiring a data rewrite. The default name Library is reserved among that owner's additional buckets.

Use the existing owner-root transaction lock for bucket creation and hierarchy mutations. New roots are valid folder parents, but cannot be changed/deleted via ordinary node routes. Additional roots are excluded from ordinary children/search results. Owner-wide searches may include children from all buckets; the UI always sends an explicit parent and searches only the current folder. Paths are relative to the containing bucket; callers must retain the bucket ID for qualification. Existing resolve(path) still resolves within default Library. New bucket APIs are session/CSRF-only; no new external bearer capabilities. Existing owner-wide tokens retain owner-wide node authority; tokens restricted to default root cannot reach separate bucket trees. Bucket-root scoped tokens are allowed. Folder restrictions follow stable folder identity, as before, and never authorize unrelated siblings or another root. Owner cleanup also deletes ms_buckets. Bucket rename/removal and scoped bucket delivery URLs are deferred; do not expose unsupported controls.

## Reference commands

Existing create/bind/rebind/rename/move/remove APIs retain their physical-file-preserving behavior. Add session-only POST /api/v1/nodes/{id}/copy with parent_id and optional name. Copy recursively clones metadata with fresh IDs in one transaction, revalidating original bindings against current accessible storage and bounding traversal to 1000 nodes and 128 levels. Root/bucket copy is forbidden. Duplicate names and unavailable bindings fail atomically. Copy into the source subtree is rejected. No credential/bearer endpoint is added. Multiple selected commands execute per root sequentially; report failures and refresh committed state, without implying batch atomicity. Clipboard stays in memory only.
