## Reproduction and observed results

```sh
npm run package
python3 tests/package_release.py
npm test
npm audit --json
MEDIASTORAGE_TEST_DISPOSABLE=yes python3 tests/release_install.py \
  --archive dist/mediastorage-0.8.0.tar.gz --browser
```

The harness needs Docker, the official images, free loopback ports 18089/18090 and the existing CDP test browser/video fixtures described in tests/README.md. It creates its own random administrator password in memory. A private temporary credential file and backup exist only for the run. It does not read Snap administrator credentials or modify Snap. Containers and anonymous volumes are removed in `finally`; abrupt process termination still requires operator cleanup by the printed `mediastorage-release-` naming prefix, never a global Docker prune.

The 197 harness checks include three child-suite exit checks; their 76/31/19 assertions are recorded separately, not added as though all were independent harness assertions.

The harness installs historical 0.2.0 from tracked commit `f57a04c` using the real Nextcloud app manager/migration runner. Before upgrade it creates an original PNG, virtual folder, binding and scoped token. It disables the app, replaces only that isolated app directory with the exact 0.8.0 archive, enables pending migrations and restarts web workers. It verifies every installed archive byte against the archive and internal manifest, then verifies preserved nodes/bindings/tokens, Library creation and actual partial delivery.

The official Apache image has `opcache.validate_timestamps=1` and `opcache.revalidate_freq=60`. Immediate web requests after code replacement initially received 503 while workers retained old code; restarting the workers resolved this. CLI app enablement alone does not invalidate another process's opcode cache. The harness makes this restart part of the installation procedure, rather than disabling opcode caching globally.

For restore, maintenance mode quiesces HTTP and no background cron service is installed. The harness snapshots `config`, `data` (including SQLite) and exact installed `custom_apps` together. It deletes a virtual reference afterward and proves the original remains. A separate fresh container first installs the exact archive successfully. Its newly created stores are then removed and replaced by the paired snapshot; maintenance mode is turned off through occ. Deleted metadata, original bytes, binding, pre-upgrade bearer token and the temporary grant are recovered together. All archive bytes and served JS/CSS match afterward. The child HTTP/browser suites run against this restored instance.

This establishes a quiesced SQLite paired restore. It does not establish an online snapshot or MySQL/PostgreSQL backup/restore. Restoring the grant also restores its pre-backup authorization state; revoke credentials again after recovery when needed. Copying older code alone is not rollback.

## Proxy and log verification

The harness generates a minimal loopback HTTP Nginx proxy with no shared cache and response/request buffering disabled. It verifies exact 206 bytes/Content-Range, HEAD length/no body, private/no-store, no CORS relaxation, 304, 412, 416 and invalid-capability 404. It preserves Host and sets forwarding headers itself. This is a local forwarding fixture, not a production TLS/Nextcloud proxy configuration or a trusted-proxy client-IP test.

Apache's `combined`/`common` log formats are explicitly overridden by `tests/fixtures/release/apache-query-redaction.conf`: log method and `%U` path, excluding query, Referer, cookies and Authorization. Nginx uses `$uri`, not `$request`/`$request_uri`/`$args`; its fixture error log threshold is `crit`. The harness inspects access-log output in memory, proves delivery requests were recorded and checks that the known capability key, bearer token and Basic credential are absent. Secrets are never printed. This verifies the configured fixture access logs, not arbitrary crash/debug/error/tracing logs or the existing Snap/proxy logs. SELinux denied the initial host bind mount; Docker copy into managed container storage works without disabling SELinux.

## Developer security review

Reviewed current controllers, stores and service boundaries in conjunction with the installed suites:

- Session management retains Nextcloud middleware/CSRF. Only explicitly public external/delivery endpoints bypass session CSRF, and they authenticate scoped bearers or bounded per-resource capabilities. Owner identity is derived from authentication; database lookups/mutations include owner filters and parameterized values. Mutations serialize at the owner's root; live tests cover conflicting writes and owner recreation on the primary target.
- Tokens/grants store SHA-256 verifiers of random secrets; comparisons use `hash_equals`. Metadata responses omit verifiers/secrets. Grant reads revalidate owner, issuer, bucket, binding/storage and original content version before conditional/range handling. Revocation/lifecycle denial is exercised live.
- Upload writes are additive, use server-generated original names under the owner's dated folder, validate MIME/size/quota and verify persisted retry identity/content rather than overwrite existing originals. Virtual Move/Remove/Clear/Delete and owner metadata cleanup do not call physical file move/delete operations. Live upgrade/restore and access tests preserve exact original bytes.
- Delivery uses bounded 64 KiB reads and public Nextcloud limiter/locking providers; disabled/unavailable protection fails closed. Installed 64 MiB distant-range and TCP-backpressured concurrency/cancellation tests pass. No full-load, process-memory, blocked-storage or crash-recovery benchmark is inferred.
- Production source review found no `v-html`, `innerHTML`, eval, unserialize or shell execution in application code, and no persistent browser credential store. The upload controller logs a generic message plus its exception; application/controller review does not replace infrastructure logging review.

This is a developer review supported by tests, not an independent penetration test or vulnerability certification. npm audit covers the npm dependency graph; Nextcloud/PHP/container operating-system security maintenance belongs to their deployment lifecycle.

## Open release gates

1. Production proxy/server access, error and tracing log redaction; TLS and actual trusted-proxy IP behavior; production upload/body/timeouts and WAF/rate rules. The existing Snap configuration was not changed.
2. Deployment-specific load/memory, stalled client/storage timeout and crash recovery tests with documented operational limits.
3. Backup/restore on the actual MySQL deployment; PostgreSQL and other Nextcloud/PHP/database combinations are unclaimed. Decide the supported release matrix before expanding claims.
4. Retained UI-10 manual acceptance: physical mobile/keyboard, actual browser zoom and every visual-state contrast. Screen-reader testing is excluded by the user.
5. Final release/signing/publication decision. No signing keys, app-store upload or public release are authorized by this test run.
